# 政府における内製か購入か

内製か購入かは、独自開発と商用あるいはコモディティ調達を、割引後の[総所有コスト](../政府itにおける総所有コスト/)、価値実現までの時間、リスクで比較する、構造化されたリスク調整済みの比較である。政府は構造的に購入するセクターである——Technology Code of Practiceはコモディティおよびクラウドソリューションへの前提を定めている——それでも、各省庁内のエンジニアリングチームは、どこでも構築者が同じ理由でそうするように、依然としてデフォルトで構築する。

## 重要な理由

Government Digital ServiceのTechnology Code of Practice（<https://www.gov.uk/guidance/the-technology-code-of-practice>）と、内製か購入かを決定することについての付随するService Manualガイダンスは、各省庁に、コモディティ能力は構築されるのではなく購入されるべきであり、真に新規でミッションを差別化する能力だけが独自コードを正当化するという前提に対して、あつらえの開発を正当化するよう迫る。2002年のMott MacDonaldによる大規模な公共調達のレビューから引き出された、Green Bookへの楽観バイアス補足ガイダンスは、IT プロジェクトに、評価される全カテゴリーの中で最も広い引き上げ幅を与えている——資本コストの見積もりは、評価に使用される前に、低い側で10%、高い側で最大200%引き上げることが推奨されている。これは、ソフトウェア構築が公共調達全体で歴史的にどれほどひどく過小評価されてきたかを反映している。内製か購入かの分析は、まさに、そのリスク調整を年度内の超過支出要求として表面化させるのではなく、承認前に俎上に載せることを強制するために存在する。

## 計算式

```
Green Bookの社会的割引率（social-discount-rateを参照）で割引
された同じ3〜5年の期間で比較する：

選択肢のNPV = PV（便益、価値実現までの時間でずらす）− PV（TCO）

リスク調整（Green Bookの楽観バイアスのパターン）：
  構築コスト × 1.1〜3.0        （ITプロジェクトの引き上げ幅、
                               Mott MacDonald）
  構築の価値実現までの時間 + 40〜60%（展開遅延の事前確率）
  購入：代わりに統合の現実チェックと契約終了コストを加える

意思決定を左右する要因、通常それが決まる順序で：
  1. 差別化——その能力はミッションなのか、それとも配管なのか？
  2. 価値実現までの時間 × 遅延コスト
     （cost-of-delay-in-public-programmesを参照）
  3. リスク調整後の総所有コスト
```

## 計算例

ある地方自治体が、成人向けソーシャルケアのケースマネジメントシステムを必要としている。購入：SaaS £180,000/年、4か月で稼働開始。構築：見積£900,000に加え£150,000/年の保守、14か月で稼働開始。

```
リスク調整後の構築コスト = 900,000 × 1.4 = £1,260,000
5年間のTCO：
  購入  = 180,000 × 5 = £900,000
  構築 = 1,260,000 + 150,000 × 5 = £2,010,000

遅延の項：そのシステムは重複したアセスメントで月£40,000を
回避する；構築は購入より10か月遅れて到着する。
遅延コスト = 10 × 40,000 = £400,000

実質的な比較：£900,000（購入）対 £2,010,000 + £400,000 =
£2,410,000（構築）
```

5年間で購入がおよそ£150万勝る。そして構築の見積もり自体の次に大きな単一の項目は、純粋な資本支出の比較では決して表面化しなかったであろう遅延コストである。

## ソフトウェア開発との関連

この分析から提供実務へ直接転用される規律がある。**事前確率に基づくリスク調整**——Mott MacDonaldの引き上げは、Green Bookの楽観バイアスを機械的に適用したソフトウェア版であり、チームは自分たちの見積もりが例外であると想定するのではなく、それに対する例外を主張すべきである。**比較対象の正直さ**——構築の代替案は「何もしない」ではなく、入手可能な最良の購入選択肢である。これは[公共支出における機会費用](../公共支出における機会費用/)に直接結びつく。そして**正直なTCO比較**——すべての構築提案は、購入選択肢の定価ではなく、その完全な[総所有コスト](../政府itにおける総所有コスト/)と比較されるべきである。構築が真に勝る場合、追加の構築時間の[遅延コスト](../公共プログラムにおける遅延コスト/)は、時間は重要ではないという述べられていない前提として残されるのではなく、ビジネスケースにおいて明示的に価格付けされるべきである。

## 落とし穴

- **ベンダーの定価をリスク調整されていない構築の見積もりと比較すること**：これは構築を二重に有利に見せる——コストで一度、スケジュールで一度。
- **ゼロ価格の内部労働**：公務員のエンジニアリング時間は、すでに省庁の頭数予算に含まれているため「無料」として扱われる。これは、そのチームが行えたであろう他の仕事に対する真の機会費用を隠す。
- **双方向の価格付けされていないロックイン**：ベンダーの離脱とデータの可搬性コストは本物であるが、あつらえの構築のバスファクターと、その存続期間にわたって維持することが難しい小規模な社内チームへの依存もまた本物である。
- **配管に対してミッションの差別化を主張すること**：統合ミドルウェアやドキュメントストアについて「これは私たちにとって中核だ」と主張すること——市民あるいはケースワーカーが、その下で何が動いているかに気づくことがあるかどうかに照らしてテストすること。
