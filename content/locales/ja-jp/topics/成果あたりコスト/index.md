# 成果あたりコスト

成果あたりコストは、総プログラム支出を、単に何らかのサービスを受けた人数ではなく、自らの状況において明確で意味のある変化を達成した人数で割ったものである。これは資金提供者や提供チームが使える最も鋭い効率性指標である。なぜなら、それはほとんどの慈善団体が避ける先行する問い——正確には何が成功とみなされるのか——を強制するからである。

## 重要な理由

フードバンクは、同じ年の会計から二つのまったく異なる数字を報告しうる。配布した食料パック1個あたりのコストは£15かもしれない。もはや緊急食料支援を必要としない——フォローアップ時点で検証された——食料安全保障を達成した世帯あたりのコストは£340かもしれない。どちらも真実である。しかし資金が機能しているかどうかを資金提供者に伝えるのは一方だけである。この二つの間のギャップは、アウトプットとアウトカムの間のギャップである——手渡された食料パックはアウトプットであり、もはや危機にない世帯はアウトカムである。[成果とアウトプット](../成果とアウトプット/)を参照。

英国の第三セクターは、この区別を強制するインフラを構築するために20年を費やしてきた。New Philanthropy Capitalの慈善団体の有効性に対する「四本柱アプローチ」は、組織にアウトプットの前にアウトカムを述べることを明示的に求めており、英国の資金提供者が支援するインパクト測定共同体であるInspiring Impactは、現在多くの助成金申請で慈善団体が記入を求められるOutcomes Matrixを公表している。Trussell TrustのHeriot-Watt大学との共同による年次「State of Hunger」研究プログラムは、まさに、パックの数だけでは人々が食料不安から抜け出せたかどうかについて何も語らないという理由で存在している。

成果あたりコストは、反実仮想を確定して初めて意味を持つ——「どのみち」達成された成果は、そのプログラムが買った成果ではない。[反実仮想分析](../反実仮想分析/)と[displacement-and-attribution](../置き換えと帰属/)を参照。

## 計算式

```
成果あたりコスト = 総プログラムコスト / 定義された成果を達成した
                  受益者数

ここで：
  総プログラムコスト = 直接提供コスト + 公正な配分の
                       オーバーヘッド
  定義された成果     = あらかじめ定められた、測定可能な状態変化
                       （例えば「6か月フォローアップ時点で
                       食料が安全である」であり、「食料パックを
                       受け取った」ではない）
```

[単位コストデータベース](../単位コストデータベース/)（例えばセクター固有の単位コストベンチマーク）と比較して、ある成果あたりコストが、比較可能な介入策と比べて良好か、平均的か、それとも劣っているかを判断すること。

## 計算例

**フードバンク、1年間**：

- 総プログラムコスト：£450,000
- 配布したパック数：30,000
- パックあたりコスト（アウトプット指標）：£450,000 / 30,000 = **£15**

この慈善団体はまた、世帯のサンプルを対象に6か月のフォローアップ調査を実施しており、パックを3個以上受け取った世帯の35%がもはや緊急食料支援を必要としないと報告し、標準的な食料安全保障調査モジュールで閾値を上回るスコアを記録していることを発見している。その年にパックを3個以上受け取った1,800世帯のうち、630世帯がその成果を達成した。

```
成果あたりコスト = £450,000 / 630 = 食料安全保障を達成した世帯
                  あたり£714
```

この£714という数字こそが、この慈善団体を現金給付パイロットや債務相談サービスと比較する資金提供者が使うべきものであり——£15ではない。もし同じ地域の比較可能な現金給付プログラムが世帯あたり£500で食料安全保障を達成しているなら、このフードバンクは、パックあたりのコストが安く見えるにもかかわらず、同じ成果への明らかにより効率的な経路ではない。

## ソフトウェア開発との関連

ほとんどのケースマネジメントシステムは、アウトプットを記録するために構築されている。なぜなら、アウトプットは取引の内部で起こること（パックが手渡される、フォームが提出される）だからである。アウトカムは通常、後になって起こり、しばしばシステムの通常の捕捉ウィンドウの外で起こるため、意図的な設計判断を必要とする——フォローアップの仕組み（調査トリガー、再連絡ワークフロー、データ連携作業）を、年次報告のために後付けされたものとしてではなく、第一級の機能として構築すること。このセクター向けの助成金管理あるいはケースマネジメントプラットフォームを構築するエンジニアは、「アウトカムイベントとは何か、そしてそれをどう観測するか」を、データモデルが固定される前に問われる要件上の問いとして扱うべきである——アウトカムフィールドをアウトプットカウンターよりも後から追加することは、はるかに困難である。この要件についての会話をどう構造化するかについては[成果とアウトプット](../成果とアウトプット/)と[ロジックモデル](../ロジックモデル/)を、アウトカム追跡がまだ構築されていない場合にチームが頼るより速く粗い指標については[受益者あたりコスト](../受益者あたりコスト/)を参照。

## 落とし穴

- **アウトプットをアウトカムに見せかけて報告すること。** 「到達した人数」は「助けられた人数」ではない。その指標がフォローアップ連絡なしのシステムログだけで生成できるなら、それはほぼ間違いなくアウトプットである。
- **分母の操作。** 成果の母集団を「プログラムを完了した人々」に狭めることは、静かに、脱落した人々——しばしば最も困難なケース——を除外し、見かけ上の達成率を膨らませる。分母は、完了した人ではなく、開始したすべての人として述べること。
- **反実仮想がないこと。** どのみち達成しただろう人々を含め、その成果を達成した全員を数えることは、そのプログラムが買ったものを過大に見積もる。[反実仮想分析](../反実仮想分析/)を参照。
- **互換性のない成果の定義を横断して比較すること。** 検証済み調査モジュールで測定された「食料が安全」は、満足度フォームで自己申告された「食料が安全」とは比較できない。成果あたりコストのリーグテーブルは、成果の定義が一致している場合にのみ誠実である。
