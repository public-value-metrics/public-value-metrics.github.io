# 政府提供におけるフロー指標

フロー指標——リトルの法則、仕掛かり作業（WIP）の制限、フロー効率——は、仕事が限られた容量を持つシステムをどれだけ速く通過するかを記述する。スプリントボードはそのようなシステムの一つである。給付請求のキュー、計画申請の登録簿、あるいはビザのケースワーク滞留は、まったく同じ数学が別の制服をまとったものである。

## 重要な理由

政府のケースロードはキューイングシステムであり、キューイングシステムは、誰かがそれを測定しているかどうかにかかわらずキューイングの法則に従う。法定の判定期間は、これを明示的にする——Town and Country Planning規制のもとでは、ほとんどの軽微な計画申請は8週間の法定判定目標を持ち、大規模な申請は13週間である——サイクルタイムの約束が法律に直接組み込まれている。National Audit OfficeとHome Affairs Select Committeeによって繰り返し精査されてきたHome Officeの亡命ケースワーク滞留は、仕掛かり作業がスループットよりも持続的に速く成長し、サイクルタイムをあらゆる法定あるいはサービス上の期待をはるかに超えて押し上げた公共システムのよく文書化された事例である。フロー指標は、エンジニアとケースワークのマネージャーの両方に、これを定性的な「滞留の問題」として残すのではなく、まさにこの失敗モードに対する共有された定量的な語彙を与える。

## 計算式

```
リトルの法則：  WIP = スループット × サイクルタイム
           →   サイクルタイム = WIP / スループット

フロー効率 = アクティブな（接触）時間 / 総サイクルタイム
            （ヴァカンティ）

WIP制限の効果：固定されたスループットに対して、WIPを半分にする
ことはおよそ平均サイクルタイムを半分にする（リトルの法則の並べ
替え）——頭数を増やすことなく使えるレバーである。
```

ケースワークではなくソフトウェアのデプロイパイプラインに適用された同等の算術については[公共価値のためのDORA指標](../公共価値のためのdora指標/)を参照。

## 計算例

**地方自治体の計画部門**：常時400件の申請がオープンしている（WIP）、チームは週50件の申請を解決する（スループット）。

```
サイクルタイム = WIP / スループット = 400 / 50 = 8週間
```

これは軽微な申請に対する法定8週間の目標にちょうど着地する——余裕がまったくなく、これは受け入れる需要あるいは協議相手の応答時間のいかなる変動性も、判定を法的締め切りを超えて押し上げることを意味する。

**フロー効率**：その8週間（暦で56日）のうち、ある申請は通常およそ6時間の実際のケースワーカー処理時間しか持たない。

```
フロー効率 = 6時間 / (56日 × 8労働時間/日)
           = 6 / 448 ≈ 1.3%
```

ソフトウェアチームに対するヴァカンティのベンチマークは、典型的なフロー効率を15〜20%としている——複数の法定協議相手への受け渡しとパブリックコンサルテーションの期間を伴う政府のケースワークは、しばしば1桁低く走る。「待機」時間の98.7%が、8週間が実際に費やされる場所である——ケースワーカーの能力ではない。

**WIP制限の介入**：ケースワーカーあたりのオープンな申請を、無制限の25件ではなく15件に上限を設けること（スループットを一定に保ちながら）は、16人のチーム全体でWIPを400からおよそ240へと移行させる。

```
新しいサイクルタイム = 240 / 50 = 4.8週間
```

スタッフの増員ではなく方針変更によるサイクルタイムのほぼ半減——これは、DORA方式の提供チームがスプリントWIPに上限を設けるときに引くのと同じレバーである。

## ソフトウェア開発との関連

フロー指標は、提供チームのカンバンボードと、そのためにソフトウェアを構築しているケースワークの現場との共有言語である——ケースワーカーのキューとプルリクエストのキューは、どちらもリトルの法則に支配されており、どちらも同じ方法でサイクルタイムの目標を吹き飛ばす——スループットに対してWIPが多すぎる。これは[公共プログラムにおける遅延コスト](../公共プログラムにおける遅延コスト/)に直接関わる——サイクルタイム × CoDは、ある瞬間にキューに座っているポンドの額である。また、これは[サービス標準と取引指標](../サービス標準と取引指標/)にも関わる。そこでは、公表された処理時間の目標はサイクルタイムの約束であり、それが逃されたとき、フロー指標だけがそれを診断できる。ケースワークシステムのソフトウェアは、誰も問い合わせないケースマネジメントシステムの中に埋もれさせるのではなく、WIPとサイクルタイムを第一級の運用指標として公開すべきである。

## 落とし穴

- **真のボトルネックを修正せずにWIP制限を追加すること**：その制約が外部の法定協議相手の応答時間である場合、ケースワーカーのWIPに上限を設けることは、キューを短縮するのではなく単に上流へ移動させるだけである。
- **フロー効率を操作対象の目標として扱うこと**：アクティブな時間の1.3%を急いでもサイクルタイムはほとんど動かない。レバレッジはほとんど常に待機状態にあり、それは通常ケースワーカーの速度ではなくプロセスの再設計を意味する。
- **変動性を無視すること**：リトルの法則は平均を記述する。需要のばらつきが大きいケースロードは、より厳しいWIP制限だけでなくバッファ容量を必要とする。そうでなければ、平均が改善しても、不安定な裾野では依然として法定締め切りが逃される。
- **WIPを一貫性なく測定すること**：記録上のシステムでは「オープン」だが実際には第三者を待って停止しているケースも依然としてWIPである。それを除外することは、市民向けの現実を変えることなく数字を良く見せかける。
