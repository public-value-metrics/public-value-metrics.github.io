# 公共価値のためのDORA指標

DORA（DevOps Research and Assessment）指標——デプロイ頻度、変更のリードタイム、変更失敗率、サービス復旧までの時間、そして五番目として信頼性——は、ソフトウェア業界で最も検証された提供パフォーマンスのベンチマークである。公共セクターの説明責任の言葉に翻訳すると、それぞれが、公共価値がどれだけ速く、どれだけ安全に市民に届くかの直接的な代理指標となる。

## 重要な理由

*Accelerate State of DevOps Report*として毎年公表される、DORAの10年にわたる研究（Forsgren、Humble、Kimの方法論、現在はGoogle Cloudが運営）は、チームをエリート、高い、中程度、低いパフォーマーにクラスター分けする。エリートチームはオンデマンドでデプロイし、コミットから本番まで1日未満で、変更のおよそ5%が失敗し、1時間未満で復旧する。低パフォーマーは月に1回以下でデプロイし、数か月かかり、変更のおよそ40%が失敗し、復旧に数週間かかる。政府においては、これらはエンジニアリング上の虚栄の指標ではない——Government Digital ServiceのService Standardは、チームに「頻繁に反復・改善する」こと、そして利用者のニーズに迅速に対応できることを求めており、安全かつ頻繁にデプロイできない省庁は、ユーザーリサーチが何を言おうとも、その標準を満たすことが構造的にできない。Cabinet Office自身のデジタル効率化の作業は、市民を失敗した、あるいは遅いデジタル取引から電話や紙のチャネルへ押し出すことが高くつくことを発見した——GDSの2012年のDigital Efficiency Reportは、一部のデジタル取引のコストがわずか20ペンスである一方、電話や対面の接触は最大£8.62かかると推定した——そのため、市民向けサービスにおける変更の失敗は、エンジニアリング時間だけでなく、実際のポンドをコンタクトセンターの予算に押し付ける（[チャネル移行による節約](../channel-shift-savings/)を参照）。

## 計算式

```
デプロイ頻度       = 本番デプロイ数 / 時間
変更のリードタイム = t(デプロイ) − t(コミット)、中央値
変更失敗率         = 失敗した変更 / 変更総数 × 100
復旧までの時間     = t(復旧) − t(障害)、中央値
                    （MTTR）
信頼性             = SLOの達成（可用性、レイテンシ、正確性）
```

公共価値への翻訳：

```
リードタイム   → パイプライン内の週数 × CoD、
                cost-of-delay-in-public-programmesを参照
失敗率         → 市民向けインシデント率：変更失敗率 × 転送された
                コンタクトセンター1通話あたりのコスト（あるいは
                失敗した法定取引あたりのコスト）
復旧時間       → サービス停止の害：MTTR ×（1時間あたりブロック
                された請求/申請数）× 単位あたりの下流コスト
                あるいは幸福損失
信頼性         → 便益割引：可用性99%のサービスは、モデル化された
                便益のおよそ0.99を提供する——利用率あるいは
                コンプライアンス不足の提供上の類似物
```

## 計算例

ある地方自治体の給付請求ポータルチーム、提供エンジニアリングへの投資の前後。

```
                    前          後
デプロイ            月1回       週1回
リードタイム        8週間       5日
変更失敗率          30%        10%
MTTR                3日        4時間
```

このチームは年間およそ25件の改善を出荷しており、平均価値は£8,000/週（[遅延コスト](../cost-of-delay-in-public-programmes/)）である。リードタイムをおよそ7.3週間削減することは、各改善の便益ストリームを前倒しする——25 × 7.3 × 8,000 ≈ **£1,460,000/年**の価値がより早く提供される。失敗率について——25 × (0.30 − 0.10) = 年間5件の失敗した変更が減る；市民向けポータルにおける失敗した変更は通常、推定2,000人の市民を電話チャネルへ転送し、£8.62対20ペンスで、1インシデントあたりおよそ£8.42×2,000 ≈ £16,840の純コストとなる。したがって5件のインシデントを回避することはおよそ**£84,200/年**を節約する。提供エンジニアリングへの投資は、他のあらゆる公共価値のケースと同じ通貨で評価される。

## 計算例続き：信頼性

そのポータルが目標の99.5%ではなく97%の可用性で稼働しており、ダウンタイムの各パーセンテージポイントが2%の請求放棄としてモデル化される場合、そのサービスはモデル化された年間£200万の便益のおよそ0.975を提供している——これは、純粋な稼働時間のダッシュボードが決して表面化しない年間£50,000の便益割引である。

## ソフトウェア開発との関連

DORA指標は、異なる衣をまとった公共サービスの運用指標である——リードタイムは[サービス標準と取引指標](../service-standards-and-transaction-metrics/)にマッピングされる；変更失敗率は手戻りと苦情率にマッピングされる；MTTRは法定サービスが請求者にとってどれだけ長く利用不能かにマッピングされる。改善手法は両方向に転用可能である。なぜなら、どちらも説明責任の制約のもとにあるキューイングシステムだからである——根底にあるキューイングの算術については[政府提供におけるフロー指標](../flow-metrics-in-government-delivery/)を参照。また、DORAの2025年の発見にも注目すること——AIの採用はより高いスループットと相関する一方で、安定性を*悪化させる*——これは有効性と副作用の両方を持つ介入策であり、まさに本章の[AI生産性](../ai-productivity-in-the-public-sector/)のトピックが取り組む純便益分析である。

## 落とし穴

- **指標の操作**：無為なリリースでデプロイ数を膨らませること、あるいはホットフィックスを変更失敗数から除外すること。イベントは、法定サービス標準が「成功した取引」を定義するのと同じくらい正確に定義すること。
- **省庁横断のリーグテーブル**：DORAのクラスターは、異なるリスクプロファイルを持つサービスではなく、提供の実務を比較している。税支払いシステムは、保証要件を考えると「エリート」が無謀であるような場所では「高い」評価が正しい姿勢かもしれない。
- **単一の指標だけを最適化すること**：変更失敗率を伴わない速度は、古典的なスループットと不安定性のトレードオフである——単一のスコアとしてではなく、四つすべてを共に報告すること。
