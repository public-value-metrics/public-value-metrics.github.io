# สร้างเองหรือซื้อในภาครัฐ

การเลือกระหว่างสร้างเองหรือซื้อคือการเปรียบเทียบอย่างเป็นระบบและปรับตามความเสี่ยงระหว่างการพัฒนาแบบเฉพาะกับการจัดหาเชิงพาณิชย์หรือสินค้าทั่วไป โดยเปรียบเทียบด้าน [ต้นทุนรวมของการเป็นเจ้าของ](../ต้นทุนรวมของการเป็นเจ้าของ-ในไอทีภาครัฐ/) ที่คิดลดแล้ว เวลาที่ใช้กว่าจะเกิดคุณค่า และความเสี่ยง ภาครัฐโดยโครงสร้างเป็นภาคส่วนที่ซื้อ — Technology Code of Practice วางข้อสันนิษฐานให้เลือกโซลูชันทั่วไปและคลาวด์ — ทว่าทีมวิศวกรรมในกระทรวงยังคงเลือกสร้างเองเป็นค่าเริ่มต้น ด้วยเหตุผลเดียวกับที่ผู้สร้างทั่วโลกทำ

## เหตุใดจึงสำคัญ

Technology Code of Practice ของ Government Digital Service (<https://www.gov.uk/guidance/the-technology-code-of-practice>) และแนวทางประกอบใน Service Manual เรื่องการตัดสินใจว่าจะสร้างหรือซื้อ ผลักดันให้หน่วยงานต้องให้เหตุผลสำหรับการพัฒนาเฉพาะกิจ โดยมีข้อสันนิษฐานว่าขีดความสามารถทั่วไปควรซื้อ ไม่ใช่สร้าง และมีเพียงขีดความสามารถที่ใหม่อย่างแท้จริงและสร้างความแตกต่างให้ภารกิจเท่านั้นที่สมควรใช้โค้ดเฉพาะ แนวทางเสริมเรื่องอคติแง่ดี (optimism bias) ของ HM Treasury ต่อ Green Book ซึ่งอิงจากการทบทวนของ Mott MacDonald ปี 2002 เกี่ยวกับการจัดซื้อภาครัฐขนาดใหญ่ ให้โครงการไอทีมีช่วงการปรับเพิ่มกว้างที่สุดในทุกประเภทที่ประเมิน — ประมาณการต้นทุนทุนแนะนำให้ปรับเพิ่ม 10% ที่ขอบล่างและสูงสุด 200% ที่ขอบบนก่อนนำไปใช้ในการประเมิน สะท้อนว่าการสร้างซอฟต์แวร์ถูกประเมินต่ำเกินไปมากเพียงใดในอดีตในการจัดซื้อภาครัฐ การวิเคราะห์สร้างหรือซื้อมีอยู่ก็เพื่อบังคับให้การปรับตามความเสี่ยงนั้นขึ้นมาอยู่บนโต๊ะก่อนอนุมัติ แทนที่จะปล่อยให้โผล่ขึ้นเป็นคำขอใช้จ่ายเกินงบกลางปี

## คณิตศาสตร์

```
เปรียบเทียบในช่วง 3–5 ปีเดียวกัน คิดลดด้วยอัตราคิดลดทางสังคม
ของ Green Book (ดู social-discount-rate.md):

NPV_ทางเลือก = PV(ประโยชน์ เลื่อนตามเวลาสู่คุณค่า) − PV(TCO)

การปรับตามความเสี่ยง (รูปแบบอคติแง่ดีของ Green Book):
  ต้นทุนการสร้าง × 1.1–3.0        (ช่วงการปรับเพิ่มสำหรับโครงการไอที, Mott MacDonald)
  เวลาสู่คุณค่าของการสร้าง + 40–60% (ความน่าจะเป็นก่อนหน้าของความล่าช้าในการติดตั้ง)
  ซื้อ: เพิ่มการตรวจสอบความเป็นจริงของการบูรณาการและต้นทุนการออกจากสัญญาแทน

ปัจจัยตัดสินใจ เรียงตามลำดับที่มักชี้ขาด:
  1. ความแตกต่าง — ขีดความสามารถนี้คือภารกิจ หรือเป็นเพียงระบบท่อ?
  2. เวลาสู่คุณค่า × ต้นทุนของความล่าช้า (ดู cost-of-delay-in-public-programmes.md)
  3. ต้นทุนรวมของการเป็นเจ้าของที่ปรับตามความเสี่ยง
```

## ตัวอย่างการคำนวณ

หน่วยงานท้องถิ่นต้องการระบบบริหารจัดการกรณีสำหรับบริการสังคมผู้ใหญ่ ซื้อ: SaaS ปีละ 180,000 ปอนด์ ใช้งานได้ใน 4 เดือน สร้าง: ประมาณการ 900,000 ปอนด์ บวกค่าบำรุงรักษาปีละ 150,000 ปอนด์ ใช้งานได้ใน 14 เดือน

```
ต้นทุนการสร้างที่ปรับตามความเสี่ยง = 900,000 × 1.4 = 1,260,000 ปอนด์
TCO 5 ปี:
  ซื้อ = 180,000 × 5 = 900,000 ปอนด์
  สร้าง = 1,260,000 + 150,000 × 5 = 2,010,000 ปอนด์

พจน์ความล่าช้า: ระบบหลีกเลี่ยงการประเมินซ้ำซ้อนเดือนละ 40,000 ปอนด์;
การสร้างมาถึงช้ากว่าการซื้อ 10 เดือน
CoD = 10 × 40,000 = 400,000 ปอนด์

การเปรียบเทียบที่แท้จริง: 900,000 ปอนด์ (ซื้อ) เทียบกับ 2,010,000 + 400,000 = 2,410,000 ปอนด์ (สร้าง)
```

การซื้อชนะประมาณ 1.5 ล้านปอนด์ในห้าปี และรายการเดี่ยวที่ใหญ่ที่สุดรองจากประมาณการการสร้างเองคือต้นทุนความล่าช้า ซึ่งการเปรียบเทียบรายจ่ายลงทุนล้วน ๆ จะไม่มีทางเผยให้เห็น

## ความเชื่อมโยงกับวิศวกรรมซอฟต์แวร์

วินัยที่ถ่ายโอนจากการวิเคราะห์นี้สู่การปฏิบัติด้านการส่งมอบโดยตรง: **การปรับความเสี่ยงบนพื้นฐานข้อมูลก่อนหน้า** — การปรับเพิ่มของ Mott MacDonald เป็นสิ่งเทียบเท่าในซอฟต์แวร์ของอคติแง่ดีใน Green Book ที่ใช้อย่างเป็นกลไก ทีมจึงควรโต้แย้งเพื่อขอข้อยกเว้นแทนที่จะสันนิษฐานว่าประมาณการของตนคือข้อยกเว้น; **ความซื่อตรงของตัวเปรียบเทียบ** — ทางเลือกอื่นของการสร้างคือตัวเลือกซื้อที่ดีที่สุดที่มี ไม่ใช่ "ไม่ทำอะไร" ซึ่งเชื่อมตรงกับ [ต้นทุนค่าเสียโอกาสในการใช้จ่ายภาครัฐ](../ต้นทุนค่าเสียโอกาสในการใช้จ่ายภาครัฐ/); และ **การเปรียบเทียบ TCO อย่างซื่อตรง** — ทุกข้อเสนอการสร้างควรเปรียบเทียบกับ [ต้นทุนรวมของการเป็นเจ้าของ](../ต้นทุนรวมของการเป็นเจ้าของ-ในไอทีภาครัฐ/) ทั้งหมดของตัวเลือกซื้อ ไม่ใช่ราคาตามรายการ ในกรณีที่การสร้างชนะจริง [ต้นทุนของความล่าช้า](../ต้นทุนของความล่าช้าในโครงการภาครัฐ/) จากเวลาสร้างที่เพิ่มขึ้นควรระบุราคาอย่างชัดเจนในกรณีทางธุรกิจ ไม่ใช่ปล่อยเป็นสมมติฐานที่ไม่ได้กล่าวถึงว่าเวลาไม่สำคัญ

## ข้อผิดพลาดที่พบบ่อย

- **เปรียบเทียบราคาตามรายการของผู้ขายกับประมาณการการสร้างที่ไม่ได้ปรับตามความเสี่ยง**: เป็นการเข้าข้างการสร้างสองเท่า ทั้งด้านต้นทุนและกำหนดการ
- **แรงงานภายในที่ตีราคาเป็นศูนย์**: เวลาของวิศวกรข้าราชการถูกมองว่า "ฟรี" เพราะอยู่ในงบบุคลากรของกระทรวงอยู่แล้ว ซึ่งซ่อนต้นทุนค่าเสียโอกาสที่แท้จริงเทียบกับงานอื่นที่ทีมนั้นทำได้
- **การผูกมัดที่ไม่ได้ตีราคาทั้งสองทิศทาง**: ต้นทุนการออกจากผู้ขายและการโอนย้ายข้อมูลเป็นของจริง แต่ปัจจัยบัสแฟกเตอร์ของระบบที่สร้างเองและการพึ่งพาการรักษาทีมภายในขนาดเล็กที่ทดแทนยากตลอดอายุของมันก็เป็นของจริงเช่นกัน
- **อ้างความแตกต่างเชิงภารกิจสำหรับระบบท่อ**: "นี่คือแก่นของเรา" ที่อ้างเกี่ยวกับมิดเดิลแวร์บูรณาการหรือที่เก็บเอกสาร — ทดสอบด้วยคำถามว่าประชาชนหรือเจ้าหน้าที่จะสังเกตเห็นหรือไม่ว่าตัวไหนทำงานอยู่เบื้องหลัง
