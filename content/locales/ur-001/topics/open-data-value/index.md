# اوپن ڈیٹا کی قدر (Open Data Value)

اوپن ڈیٹا کی قدر یہ مسئلہ ہے کہ حکومتی اور عوامی ڈیٹا کی قیمت کا تخمینہ کیسے لگایا جائے جب اس کی
کوئی قیمت مقرر نہ ہو: یہ فروخت نہیں ہوتا، اس لیے اس کی کوئی آمدنی کی مد نہیں، پھر بھی اسے جاری کرنا
(موسمی ریکارڈ، ٹرانسپورٹ کے اوقات کار، پوسٹ کوڈ کی حدود، کمپنی رجسٹر) واضح طور پر نیچے کی سطح پر
معاشی اور سماجی سرگرمی پیدا کرتا ہے۔ اسے صحیح طور پر قدر دینا اس لیے اہم ہے کیونکہ "اسے جاری کرنا
مفت ہے" اور "یہ بے قدر ہے" دونوں غلط ہیں، اور ایک سافٹ ویئر انجینئر جو کسی API یا ڈیٹاسیٹ کو کھولنے
کا فیصلہ کر رہا ہے اسے دونوں سے بہتر دلیل درکار ہوتی ہے۔

## یہ کیوں اہم ہے

سب سے زیادہ حوالہ دیا جانے والا اوپر سے نیچے تخمینہ McKinsey Global Institute کی 2013 کی رپورٹ
"Open data: Unlocking innovation and performance with liquid information" سے آتا ہے، جس نے سات
شعبوں — تعلیم، ٹرانسپورٹ، صارفی مصنوعات، بجلی، تیل اور گیس، صحت کی دیکھ بھال، اور صارفی مالیات —
میں اوپن ڈیٹا کی ممکنہ سالانہ قدر کا تخمینہ عالمی سطح پر $3 ٹریلین سے $5 ٹریلین سالانہ لگایا، جو
بڑھتی ہوئی شفافیت، طلب و رسد کو زیادہ مؤثر طریقے سے ملانے، اور ڈیٹا پر بننے والی نئی مصنوعات اور
خدمات جیسے میکانزم کے ذریعے ممکن ہے۔ یہ ایک منظرنامے کا تخمینہ ہے، کوئی ناپا ہوا نتیجہ نہیں، اور اسے
اکثر غلط طور پر ایسے پیش کیا جاتا ہے جیسے یہ آمدنی ہو جسے حکومت براہِ راست حاصل کر سکتی ہو، جبکہ
اکثر و بیشتر قدر تیسرے فریقوں — کاروباروں، محققین، شہریوں — کو حاصل ہوتی ہے جو یہ ڈیٹا استعمال کرتے
ہیں، اور یہی بات اسے فروخت کرنے کی بجائے کھولنے کا اصل مقصد ہے۔ برطانیہ کے Open Data Institute نے،
جسے Sir Tim Berners-Lee اور Sir Nigel Shadbolt نے 2012 میں مشترکہ طور پر قائم کیا، تب سے زیادہ
باریک، نیچے سے اوپر کیس اسٹڈیز کا ایک ذخیرہ تیار کیا ہے — شعبہ در شعبہ، ڈیٹاسیٹ در ڈیٹاسیٹ — جو کسی
حقیقی کاروباری معاملے کے لیے McKinsey کے سرخی نما عدد سے کہیں زیادہ مفید ہیں، کیونکہ وہ قدر پیدا
ہونے کا میکانزم دکھاتے ہیں، نہ کہ محض اس کا مجموعی حجم۔

## ریاضیاتی بنیاد

اوپن ڈیٹا کی کوئی مارکیٹ قیمت نہیں ہوتی، اس لیے قدر گزاری کے طریقے اس کی جگہ لیتے ہیں؛ تین طریقے
بار بار سامنے آتے ہیں، اور کوئی بھی اکیلا کافی نہیں:

```
1. Cost-avoided / replacement-cost method:
   value ≈ what users would have paid to produce or licence the
   equivalent data themselves — a lower bound, ignores value created
   by uses the original producer never anticipated

2. Market-analogue / downstream-activity method:
   value ≈ revenue or savings generated by businesses/services built
   on the data (e.g. satnav apps built on open mapping and traffic
   data) — captures real economic activity but is hard to attribute
   cleanly to the data release itself (see additionality-and-deadweight)

3. Contingent/stated-preference method:
   value ≈ what users say they would pay, or the time they say it
   saves them — see stated-preference-valuation for the general
   method and its biases

None of these produces a figure as clean as a market price; credible
open data business cases triangulate across two or more, and are
explicit about which mechanism is doing the work.
```

## عملی مثال

**ایک مثالی قومی نقشہ سازی/پتہ ڈیٹا کا اجراء** (طریقہ کار ODI طرز کی کیس اسٹڈیز کے بعد، اعداد و شمار
اس پیمانے کی مثال ہیں جو ایسی اسٹڈیز عام طور پر پاتی ہیں):

```
Cost-avoided estimate:
  Businesses that would otherwise licence equivalent address-matching
  data commercially, at an estimated average licence cost of £4,000/
  year, across an estimated 15,000 SMEs now using the free open dataset
  = 15,000 × £4,000 = £60,000,000/year in avoided licensing cost alone

Downstream-activity estimate (more speculative, needs a counterfactual):
  New delivery-routing and logistics products built on the open data
  that would not exist, or would be materially worse, without it —
  requires a comparison against the counterfactual of the data staying
  closed or commercially licensed (counterfactual-analysis), because
  some of that activity would happen anyway on paid data at a higher
  price, which is deadweight in the "value created by opening it" sense

A defensible business case reports the cost-avoided figure as the
solid lower bound, and treats the downstream-activity figure as an
upper-bound scenario, not a fact.
```

## سافٹ ویئر انجینئرنگ سے تعلق

انجینئرز کے لیے، عملی اوپن-ڈیٹا-قدر کا سوال عام طور پر قومی سرخی والے اعداد و شمار سے کہیں زیادہ
تنگ ہوتا ہے: کیا اس مخصوص API یا ڈیٹاسیٹ کو کھولنا (بجائے اسے کسی پارٹنر معاہدے کے پیچھے رکھنے کے)
اسے دستاویز کرنے، ورژن بنانے، اور اسے عوامی انٹرفیس کے طور پر سپورٹ کرنے کی جاری لاگت کا جواز پیش
کرنے کے لیے کافی حد تک دوبارہ استعمال بڑھاتا ہے؟ یہ دیکھ بھال کی لاگت حقیقی ہے اور
[گورنمنٹ-بطور-پلیٹ فارم](../government-as-a-platform/) کی ایک-بار-بناؤ-بار-بار-استعمال-کرو معاشیات
کا ہم پلہ ہے — یہ دونوں موضوعات قریبی رشتہ دار ہیں، ایک مشترکہ کوڈ اور بنیادی ڈھانچے کے بارے میں،
دوسرا مشترکہ ڈیٹا کے بارے میں۔ کسی بھی اوپن ڈیٹا قدر کے دعوے کو کاروباری معاملے میں شامل کرنے سے
پہلے [اضافیت اور ڈیڈویٹ](../additionality-and-deadweight/) کے خلاف جانچنا چاہیے: وہ سرگرمی جو
کمرشل طور پر لائسنس شدہ ڈیٹا پر بہرحال ہو جاتی، وہ قدر نہیں جو *کھولنے* نے پیدا کی۔

## ممکنہ خامیاں

- **McKinsey کے $3–5 ٹریلین کے عدد کو برطانیہ کے مخصوص یا اس ڈیٹاسیٹ کے حصے کے طور پر پیش کرنا**:
  یہ 2013 کا ایک عالمی، سات شعبوں پر مبنی منظرنامے کا تخمینہ ہے — اسے کسی ایک قومی ڈیٹاسیٹ کے لیے
  درست ضرب کے طور پر استعمال کرنا اس عدد کی غلط نمائندگی کرتا ہے۔
- **کوئی کاؤنٹرفیکچوئل نہ ہونا**: اوپن ڈیٹا پر بننے والی تمام نیچے کی معاشی سرگرمی کا کریڈٹ لے لینا،
  یہ پوچھے بغیر کہ اس میں سے کتنی بہرحال ادا شدہ یا لائسنس شدہ ڈیٹا پر زیادہ قیمت پر ہو جاتی
  (دیکھیں [اضافیت اور ڈیڈویٹ](../additionality-and-deadweight/) اور
  [کاؤنٹرفیکچوئل تجزیہ](../counterfactual-analysis/))۔
- **پیداواری لاگت کو پیدا ہونے والی قدر سے گڈمڈ کرنا**: کوئی ڈیٹاسیٹ جو جمع کرنا مہنگا تھا اسے
  خودبخود جاری کرنا فائدہ مند نہیں ہوتا، اور کوئی سستا ڈیٹاسیٹ خودبخود کم قدر کا نہیں ہوتا — قدر
  نیچے کے استعمال کی پیروی کرتی ہے، نہ کہ اوپر کی لاگت کی۔
- **"اوپن" کی جاری دیکھ بھال کی لاگت کو نظر انداز کرنا**: ایک بار CSV نکالنا شائع کرنا وہی عزم نہیں
  جو ایک دستاویزی، ورژن شدہ، سپورٹڈ اوپن API چلانا ہے — لانچ کے اعلان کے بعد بعد الذکر کے لیے کم
  فنڈنگ دینا ایک عام ناکامی کا نمونہ ہے۔
