# 面向公共价值的 DORA 指标（DORA Metrics for Public Value）

DORA（DevOps Research and Assessment，DevOps 研究与评估）指标——部署频率、变更前置时间、变更失败率、服务恢复时间，加上作为第五项的可靠性——是软件行业验证最充分的交付绩效基准。转化为公共部门问责制的语言后，每一项都直接代理着公共价值到达公民手中的速度与安全程度。

## 为何重要

DORA 长达十年的研究，以《Accelerate DevOps 现状报告》（*Accelerate State of DevOps Report*）的形式每年发布（Forsgren、Humble 和 Kim 提出的方法论，如今由 Google Cloud 运营），将团队分为精英级、高绩效、中等绩效和低绩效四类。精英团队按需部署，从提交到生产环境用时不到一天，变更失败率约为 5%，恢复时间不到一小时；低绩效团队每月部署一次或更少，用时数月，变更失败率约为 40%，恢复需要数周。在政府领域，这些不是工程虚荣指标：政府数字服务局的服务标准要求团队"频繁迭代与改进"，并能快速响应用户需求，而那些无法安全、频繁部署的部门，无论其用户研究结果如何，在结构上都无法达到这一标准。内阁办公室自身的数字效率研究发现，将一位公民从失败或缓慢的数字交易推向电话或纸质渠道代价高昂——GDS 2012 年的《数字效率报告》估计，某些数字交易的成本低至 20 便士，而电话或面对面接触的成本可高达 8.62 英镑——因此面向公众服务中的一次变更失败，不仅耗费工程时间，还会将真金白银推向呼叫中心预算（参见[渠道转移节约](../channel-shift-savings/)）。

## 数学原理

```
部署频率        = 生产环境部署次数 / 时间
变更前置时间    = t(部署) − t(提交)，取中位数
变更失败率      = 失败变更数 / 变更总数 × 100
服务恢复时间（MTTR） = t(恢复) − t(故障)，取中位数
可靠性          = 服务级别目标（SLO）达成率（可用性、延迟、正确性）
```

公共价值转化：

```
前置时间   → 流水线中滞留的周数 × 延迟成本，参见 cost-of-delay-in-public-programmes
失败率     → 面向公民的事件率：变更失败率 × 每次被转移到呼叫中心
             的通话成本（或每一次失败的法定交易成本）
恢复时间   → 服务中断损害：MTTR × （每小时被阻塞的申领/
             申请数）× 单位下游成本或福祉损失
可靠性     → 效益折扣：一项可用性为 99% 的服务，实际交付其
             建模效益的约 0.99——这是采用率或合规缺口在
             交付层面的对应物
```

## 实例演算

某地方政府福利申领门户团队，在一项交付工程投资前后的表现：

```
                    之前        之后
部署                每月一次    每周一次
前置时间            8 周        5 天
变更失败率          30%         10%
MTTR                3 天        4 小时
```

该团队每年上线约 25 项改进，平均每项价值为每周 8,000 英镑（[延迟成本](../cost-of-delay-in-public-programmes/)）。将前置时间缩短约 7.3 周，使每项改进的效益流提前到来：25 × 7.3 × 8,000 ≈ **每年 1,460,000 英镑**的价值被更早交付。就失败率而言：25 × (0.30 − 0.10) = 每年减少 5 次失败变更；一个面向公众的门户上的一次失败变更，通常估计会将约 2,000 名公民转移至电话渠道，成本为 8.62 英镑对比 20 便士，净成本约为每起事件 8.42 × 2,000 ≈ 16,840 英镑，因此避免 5 起事件可节省约**每年 84,200 英镑**。这项交付工程投资，是以与任何其他公共价值论证相同的"货币"来估值的。

## 实例演算续：可靠性

如果该门户的可用性为 97%，而非目标的 99.5%，且每一个百分点的宕机时间被建模为 2% 的申领因放弃而流失，那么该服务实际交付的效益约为其建模的每年 200 万英镑效益的 0.975——这是一笔每年 50,000 英镑的效益折扣，一个纯粹的正常运行时间仪表盘永远不会揭示出这一点。

## 与软件工程的关联

DORA 指标其实是公共服务运营指标换了一套外衣：前置时间对应[服务标准与交易指标](../service-standards-and-transaction-metrics/)；变更失败率对应返工率和投诉率；MTTR 对应一项法定服务对申领人不可用的时长。改进技术可以双向迁移，因为两者本质上都是在问责制约束下运行的排队系统——关于其背后的排队论数学，参见[政府交付中的流动指标](../flow-metrics-in-government-delivery/)。另请留意 DORA 2025 年的发现：AI 的采用与更高的吞吐量相关，但也与*更差*的稳定性相关——这是一项兼具功效与副作用的干预措施，正是本章[AI 生产力](../ai-productivity-in-the-public-sector/)主题所要梳理的那种净收益分析。

## 常见陷阱

- **指标操纵**：用无实际意义的空发布来虚增部署计数，或将热修复排除在变更失败计数之外。应像法定服务标准定义"成功交易"那样精确地定义各类事件。
- **跨部门排行榜**：DORA 分级比较的是交付实践，而不是风险特征各异的服务；一个税款支付系统被评为"高绩效"可能恰恰是正确的姿态，因为考虑到保证要求，"精英级"反而可能是轻率的。
- **单独优化某一项指标**：只追求速度而不顾变更失败率，是经典的吞吐量与稳定性权衡陷阱——应将四项指标一并报告，而不是压缩成单一分数。
