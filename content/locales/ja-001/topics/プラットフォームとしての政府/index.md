# プラットフォームとしての政府（GaaP）

Government as a Platformは、通知サービス、支払いサービス、身元確認サービスのような共有され再利用可能なコンポーネントを、それぞれの個別サービスが独自に構築するのではなく、一度、中央集権的に構築し、何百もの個別の政府サービスがそれを消費するという戦略である。これは、公共デジタルインフラを、プラットフォーム経済学の問題として再構成する——価値はどれか一つの統合にあるのではなく、それを採用する*次の*チームの限界費用がゼロに近づくことにある。

## 重要な理由

GDSは、2015年の「Government as a Platform」の発表でこの戦略を正式に定めた。政府は、支払いの受け取り、利用者への通知、身元確認、住所検索のような同じ能力を、サービスごとに別々に構築しており、それぞれが独自の調達、セキュリティ評価、継続的なサポート負担を抱えているという主張であった。その代替案は、一度高い標準で構築され、あらゆる場所で再利用される少数の共有プラットフォームであった——電子メール、テキストメッセージ、手紙を送るGOV.UK Notify、オンライン支払いを受け取るGOV.UK Pay、そして身元確認のためのGOV.UK One Login（以前のGOV.UK Verify身元確認プログラムの後継）である。これらのプラットフォームが到達した規模こそが、その戦略が機能したことの最も明確な証拠である——GOV.UK Payは、およそ1,800の個別サービスにわたって£100億を超える取引を処理してきた——そして最初の£10億を処理するのにおよそ4年かかったのに対し、現在はそれをおよそ5か月で処理する——一方でGOV.UK Notifyは1,500を超える政府組織に代わって90億件を超えるメッセージを送ってきた。それらを採用したサービスのそれぞれが、独自の支払いゲートウェイあるいはメッセージングパイプラインを構築・保護・保守することを回避した。

## 計算式

```
サービスあたりの構築コスト（プラットフォームなし） = Nサービス ×
  一つの支払い/通知/身元確認システムを構築、セキュリティ評価、
  運用するコスト

プラットフォームコスト = 固定のプラットフォーム構築コスト
                        + 採用するサービスあたりの限界コスト
                          （統合、設定、継続的なプラットフォーム
                          チームのサポート）

再利用は以下の時点で損益分岐点に達する：
  プラットフォーム構築コスト < N ×（サービスあたりの構築コスト
  − 限界統合コスト）

成熟したプラットフォームでは、追加の採用者あたりの限界コストは
取引/メッセージ料金だけに近づく——固定コストは一つの省庁の予算
ではなく政府資産全体にわたって償却される。これが、GaaPの
コンポーネントが通常、早期採用者にフルコスト回収で請求される
のではなく中央で資金提供される理由である。
```

## 計算例

**支払いゲートウェイを構築する代わりにGOV.UK Payを採用する地方自治体**：

```
自前構築の見積もり：
  PCI-DSSコンプライアンス作業＋統合＋継続的な保守
  ≈ £85,000構築＋£22,000/年の保守

GOV.UK Payの採用：
  統合作業 ≈ £12,000（開発者時間）
  取引手数料：政府対市民のカード支払いは通常、取引あたり小さな
  パーセンテージ＋固定手数料で課金され、議会が負担する別途の
  PCI-DSS負担はない
  ≈ £12,000の一回限り、継続コストは固定ではなく量に応じて変動

初年度の節約 ≈ £85,000 − £12,000 = £73,000、回避された年間
£22,000の保守と、カードデータを議会運営のシステムに保持すること
自体の回避されたコンプライアンスリスクを数える前の数字である
——この二番目のカテゴリーは、public-sector-cybersecurity-value
で扱われるセキュリティ価値である。
```

その£73,000を、現在GOV.UK Payを使っているおよそ1,800のサービスにわたって規模拡大すると、政府全体にわたる回避された構築コストの合計は数億に及ぶ——戦略の価値が実際に存在するのは、どれか一つの統合ではなく、プラットフォーム経済学である。

## ソフトウェア開発との関連

Government as a Platformは、[政府における内製か購入か](../政府における内製か購入か/)に対する直接的な論拠である——共有され、評価され、うまく運営されているコンポーネントが存在する場合、あつらえの同等物を構築することは、ほとんどの場合、より良い[バリュー・フォー・マネー](../物有所値/)の選択ではなく、ほぼ定義上[デジタルサービス標準](../デジタルサービス標準/)の第13項目（「オープン標準、共通コンポーネント、パターンを使用し貢献する」）に不合格になる。これはまた、[政府ITにおける総所有コスト](../政府itにおける総所有コスト/)の形も変える——プラットフォームの採用は、大きな資本・保守の項目を、予測しやすく、サービスが廃止された際に資金を引き上げやすい、より小さな使用量に連動した運用コストへと交換する。コンポーネントのオープンな再利用には、[オープンデータの価値](../オープンデータの価値/)にいとこがいる——どちらも、政府が一度生み出したものを省庁の資産としてではなく共有インフラとして扱う戦略である。

## 落とし穴

- **影の再構築**：プラットフォームのオンボーディングプロセスが自分たちでやるよりも遅いという理由で、チームが静かに独自の支払いあるいは通知の統合を構築すること——これはテクノロジーの問題ではなくガバナンスの摩擦の問題であり、戦略全体が依存する再利用の経済学を静かに侵食する。
- **それが生み出す価値に対してプラットフォームチームに資金不足であること**：価値は消費する省庁に発生する一方でコストはプラットフォームチームに座っており、資金が中央集権化され保護されない限り慢性的な過少投資のリスクを生む——コモンズの悲劇の一種である。
- **プラットフォームの成功を利用だけで測定すること**：採用の数字（オンボーディングされたサービス数、送信されたメッセージ数）は先行指標であり、価値の証明ではない。真のテストは、上記の回避された構築コストと回避されたリスクの算術である。
- **「プラットフォーム」を「モノリス」と同義に扱うこと**：GaaPのコンポーネントが成功するのは、それぞれが狭く安定したインターフェースで一つのことをうまく行うからである——無関係な能力を一つの「プラットフォーム」に束ねることは、異なる規模であつらえの構築の問題を再現する。
