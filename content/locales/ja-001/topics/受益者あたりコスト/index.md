# 受益者あたりコスト

受益者あたりコストは、総プログラムコストを、サービスを受けたユニークな人数で割ったものである——実際に状況が変化したかどうかにかかわらず、接触した誰もが含まれる。これは組織が生み出せる最も速い効率性の数字である。なぜなら「誰にサービスを提供したか」はほとんど常にすでにケースマネジメントシステムにある一方、「誰が助けられたか」は通常そうではないからである。

## 重要な理由

資金提供者は絶えず受益者あたりコストを求める。それには擁護可能な理由がある——即座に入手可能であり、非常に異なるプログラムのポートフォリオ全体で比較可能であり、そして検証に時間がかかり過大に主張されやすい成果の主張とは異なる形で、リーチについて正直である。FRS 102のもとで慈善団体がどう報告するかを規律するUK Charities SORP（推奨実務に関する声明）は、受託者の年次報告書が目標に対する達成を記述することを求めているが、ほとんどの小規模な慈善団体の経営会計は依然として、生成が安価で監査に適しているという理由で、リーチベースの単位コストをデフォルトとしている。

危険なのは、受益者あたりコストが答えられない問い——お金が機能したかどうか——に答えているかのように扱うことである。実際にそれに答える指標については[成果あたりコスト](../成果あたりコスト/)を、根底にある区別については[成果とアウトプット](../成果とアウトプット/)を参照。受益者あたりコストは正当なトリアージとリーチの指標である——それは資金提供者に、お金がどれだけ広がるかを伝える——しかし低い受益者あたりコストは、本物の効率性を意味することもあれば、何も変えないほど薄いサービスを意味することもある。

## 計算式

```
受益者あたりコスト = 総プログラムコスト / サービスを受けたユニークな
                     人数

対比：
成果あたりコスト   = 総プログラムコスト / 定義された成果を達成した
                     人数

受益者あたりコストは常に成果あたりコスト以下である。なぜなら、
成果の母集団は受益者母集団の（しばしば小さな）部分集合だからである。
```

## 計算例

**フードバンク、成果あたりコストの例と同じ年**：

- 総プログラムコスト：£450,000
- サービスを受けたユニークな世帯数（パック3個以上）：1,800

```
受益者あたりコスト = £450,000 / 1,800 = サービスを受けた世帯あたり
                     £250
```

二つの指標を並べて比較する。

| 指標 | 分母 | 結果 |
|---|---|---|
| 受益者あたりコスト | サービスを受けた1,800世帯 | £250 |
| 成果あたりコスト | 食料安全保障を達成した630世帯 | £714 |

£250だけを見る資金提供者は、これが非常に効率的な慈善団体だと結論づけるかもしれない。両方の数字を見る資金提供者は、より有用な問いを尋ねることができる——リーチ（1,800）と成果（630）の間のギャップは、データ収集のギャップなのか、設計上のギャップなのか、それとも食料支援だけで食料安全保障を達成することがいかに難しいかの正直な反映なのか。

**職業訓練慈善団体、例示**：受益者あたりコスト（登録）=£2,000；成果あたりコスト（6か月時点での持続的な就労）=£11,000、これは登録者のわずか18%しかプログラムを完了し持続的な仕事を見つけないためである。完了率あるいは持続率が低い場所ではどこでも、この二つの数字が5倍もの差で乖離することは一般的である——職業訓練慈善団体とフードバンクは、ここでは構造的に同一である。

## ソフトウェア開発との関連

受益者あたりコストは、非営利ソフトウェアにおけるデフォルトの指標である。なぜなら、それは受益者レコードからさらなる作業なしに自然に得られる指標だからである——ケースを作成し、サービスを記録し、行を数える。成果あたりコストもサポートするシステムを構築することは、第二の第一級エンティティ——サービス提供とは独立して日付が付けられ定義されたアウトカムイベント——を意図的に追加し、「ケースがクローズされた」を「成果が達成された」の代役として使いたい誘惑に抵抗することを意味する。助成金管理あるいはCRMプラットフォームの範囲を定める際には、各ダッシュボードが実際にどちらの指標を示しているのかを問い、それに応じてラベルを付けること。この二つを単一の「インパクト」タイルに混同することは、下記の落とし穴の最も一般的なソフトウェアレベルの原因の一つである。どちらの指標も正しくラベル付けされた後にベンチマークする方法については[単位コストデータベース](../単位コストデータベース/)を参照。

## 落とし穴

- **受益者あたりコストをインパクトとして提示すること。** それはリーチを測定するのであり、変化を測定するのではない。ダッシュボードと報告書には「サービスを受けた人あたりコスト」とラベルを付けること。「助けられた人あたりコスト」ではない。
- **プログラム間での二重計上。** 同じ慈善団体から食料パックと債務相談の両方を受けている人は、分母がユニークなリーチを記述することを意図している場合、二人ではなく一人の受益者である。どちらの規約を使うかを決定し文書化すること。
- **低い数字を常に良いものとして扱うこと。** 立ち寄り式のランチクラブは、受益者あたりコストで常に集中的なケースマネジメントサービスに勝る。なぜなら、軽く接触するほうが安上がりだからである。それは、どちらが1ポンドあたりより持続的な変化を生むかについては何も語らない。
- **報告書間で分母を静かに入れ替えること。** ある年次報告書では「登録」に対して、次の年次報告書では「完了」に対して引用された受益者あたりコストの数字は、年をまたいで比較できない。毎回分母を明示すること。
