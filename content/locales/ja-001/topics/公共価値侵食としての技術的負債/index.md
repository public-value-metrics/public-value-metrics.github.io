# 公共価値侵食としての技術的負債

技術的負債は、ウォード・カニンガムによる1992年の比喩であり、便宜的な過去のコーディング上の決定が暗示する将来のコストを表す——**元金**（負っている是正作業）と**利子**（それが提供に及ぼし続ける足かせ）である。レガシーな政府ITの資産において、その利子は公共価値から直接支払われる——より遅い法定変更の提供、市民向けサービスにおけるより高い失敗率、そしてそのシステムに安全に触れられる人々の縮小するプールである。

## 重要な理由

英国政府の各省庁にわたるレガシーなメインフレームとCOBOL時代のシステム——HMRCとDWPが最もよく引用される——は、National Audit Officeがその報告書『Digital Transformation in Government』（<https://www.nao.org.uk/>）を含め繰り返しフラグを立ててきた、よく文書化されたエスカレートするリスクを抱えている——変更が高くつき、ますますセキュリティを確保するのが難しく、代替されるよりも速く退職している専門的な労働力に依存している老朽化したプラットフォームである。民間セクターの滞留とは異なり、この負債は市民とその法定受給資格の間に直接位置する——安全に変更できない給付計算エンジンは、単なるエンジニアリング上の不便さではなく、政策提供上の制約である。2013年のUniversal Credit ITプログラムの再スタート——National Audit Officeが元の構築がバリュー・フォー・マネーを提供しないことを発見し、そのソフトウェア資産のかなりの部分を償却しなければならなかった——は、価格付けされなかった技術的負債が、生きた、閣僚レベルで目に見える公共プログラムに追いつく典型的な事例である。

## 計算式

```
SQALE元金 = Σ 違反にわたって（是正時間）× 開発者コスト率
技術的負債比率（TDR） = 是正コスト / 再開発コスト × 100
                    （SonarQubeの等級：A≤5%、B≤10%、C≤20%、D≤50%）

利子（返済を正当化する数字）：
  利子/年 = Δ提供速度 × 単位速度あたり価値
          + Δ市民向けインシデント率 × インシデントあたりコスト
          + 専門スキルのプレミアム × 影響を受けた頭数
返済のケース = PV（期間にわたって回避された利子）− 是正コスト
              （Green Bookの社会的割引率で割引、
              social-discount-rateを参照）
```

元金は負債を述べ、利子はそれを公会計委員会に対する投資のケースにするものである。

## 計算例

レガシーな第4世代言語で書かれた25万行の請求処理エンジン。1コード行あたりおよそ$3.61の技術的負債元金というCAST Appmarqベンチマークを使用（典型的な換算で≈£2.85）。

```
元金 ≈ 250,000 × £2.85 ≈ £712,500
TDR ≈ 16%（等級C）
```

測定された利子：社内スキルが摩耗したため、その省庁は標準的なシニアエンジニアのレートより40%高い日額プレミアムで3人の専門契約者を維持している——6人チームで年間追加£180,000。このシステムはまた、年間4回の大規模な処理停止を引き起こし、それぞれがおよそ5,000人の請求者の決定を一時停止し、通話あたりおよそ£25でコンタクトセンターへ転送する。

```
利子 ≈ £180,000（スキルプレミアム）
     + 4 × 5,000 × £25 = £500,000（転送された接触のコスト）
     ≈ £680,000/年
```

最も業績の悪いモジュールの対象を絞った是正には£1,200,000かかり、利子を70%削減するとモデル化される。

```
利子の削減 = 0.70 × 680,000 = £476,000/年
回収期間 ≈ 1,200,000 / 476,000 ≈ 2.5年
```

ターゲティングが重要である——めったに触れられないコードを是正しても何も買わない。なぜなら、利子は変更頻度と負債密度の両方がピークとなる場所に集中するからである。

## ソフトウェア開発との関連

技術的負債のケースを「コードが古い」以上へと引き上げる公共価値の枠組みは、レガシー資産を、失われた提供能力がどこに集中しているかの目録として表現し、それを[総所有コスト](../政府itにおける総所有コスト/)に明示的に結びつけることである。なぜなら、利子は財務がそれを尋ねたことがあるかどうかにかかわらずTCOの行に属する運用コストだからである。負債を抱えたシステムはまた、不均衡な[サイバーセキュリティ](../公共セクターのサイバーセキュリティの価値/)へのエクスポージャーも抱える。なぜなら、パッチの頻度と負債密度は相関しているからである——パッチを当てられないレガシーシステムは、その利子がポンドではなくインシデントリスクで支払われる技術的負債である。そして、是正対機能というあらゆるトレードオフ自体が[遅延コスト](../公共プログラムにおける遅延コスト/)の決定である——負債の返済は次の法定変更を遅らせ、それ自体が独自のCoDを持ち、節約された利子と天秤にかけられなければならない。

## 落とし穴

- **元金だけの報告**：利子の数字を伴わない大きく恐ろしい是正の見積もりは、支出承認者に対して何も正当化しない。
- **ツールが生成した負債の数字を額面通りに受け取ること**：SQALE方式のスキャナーはルール違反を数える——それらは高くつく種類の負債——アーキテクチャ上の決定と文書化されていないレガシーのビジネスルール——を見逃す一方で、些細なことにフラグを立てる。
- **「書き直せばすべて回避できる」**：置き換えプログラムは、2013年のUniversal Creditの再スタートが示したように、それを免除されるのではなく、他のあらゆるビジネスケースと同じ規律——反実仮想のコスト、成功の確率、割引——をクリアしなければならない。
- **負債ゼロのユートピア主義**：最適な負債水準はゼロではない——負債は、より早い提供を買ったレバレッジである。生きた問いは常に金利であり、負債がそもそも存在するかどうかではない。
