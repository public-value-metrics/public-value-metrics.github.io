# デジタルサービス標準

GOV.UK Service Standardは、すべての中央政府デジタルサービスが稼働開始できるようになる前に通過しなければならないゲートである——各提供フェーズの終わりに独立したパネルによって評価される、14の公表された項目である。これは、「良い公共サービスを構築する」というスローガンを、書類の証跡を伴う合格/不合格の決定へと変える仕組みであり、2012年のGovernment Digital Strategyの「デフォルトでデジタル」という命令の直系の子孫である。

## 重要な理由

Service Standardが存在する前は、政府ITの失敗はローンチまで目に見えることがめったになく、誰かが指摘できる決定に帰属することもめったになかった。2012年のGovernment Digital Strategyは、各省庁に、最も取引量の多い25の市民向け取引サービスを「デフォルトでデジタル」として再設計することを約束させ、その約束をコンプライアンスの仕組みで裏付けた——サービスは、当時26項目であった標準（2019年に18項目に統合され、現在は3つのグループ——利用者のニーズを理解すること、良いサービスを提供すること、正しい技術を使うことをカバーする、現在有効な14項目の標準）に対するサービス評価をクリアしなければ、GOV.UK上で稼働開始できなかった。サービス評価は実際の出来事である——GDSあるいは省庁の評価者からなるパネルがエビデンスをレビューし、チームに質問し、各項目について合格、不合格、あるいは「未達成」の判定を下し、そのサービスの評価ページに公表する。評価に不合格になることは、サービスがプライベートベータからパブリックベータへ、あるいはベータからライブへ移行することを阻止する——それは実際のゲートであり、レビューではない。

## 計算式

Service Standardは枠組みであり公式ではないが、段階ゲート型の意思決定構造として機能する。

```
発見 → アルファ評価 → ベータ評価 → ライブ評価
       （すべてのサービスに必須ではないが、（パブリックベータ  （「ベータ」タグを
        推奨される）              ローンチ前に必須）  外し旧チャネルを閉鎖
                                                       する前に必須）

各評価：エビデンス＋チームインタビュー → 項目ごとのパネルの判定
  達成 / 部分的に達成 / 未達成
総合結果：合格 / 条件付き合格 / 不合格（再評価が必要）

不合格のコスト ≈ 是正するための次のスプリントサイクルのコスト
              + そのサービスが提供する資金を得ていた
                [チャネル移行による節約](../channel-shift-savings/)
                の遅延
```

第10項目（「成功とは何かを定義し、業績データを公表する」）が、[取引あたりコスト](../cost-per-transaction/)と[サービス標準と取引指標](../service-standards-and-transaction-metrics/)に供給するものである——この標準は、サービスだけでなく測定そのものを義務付けている。

## 計算例

**地方自治体の住宅申請サービス**：ある議会のチームが、14項目のうち11項目を達成するサービスでベータ評価に到達するが、インターネットアクセスのない申請者向けの支援付きデジタル経路が存在しないため第5項目（「誰もがそのサービスを使えるようにする」）に不合格となり、個人データがプレーンテキストのアプリケーションエラートレースに記録されているため第9項目に不合格となる。

```
不合格の直接コスト：
  再評価の枠：次に利用可能なパネルまで6〜8週間の待機
  是正スプリント：開発者2人 × 3週間 × £550/日 ≈ £34,650
  支援付きデジタルチャネルの設計：研究者1人 × 2週間 ≈ £5,000

遅延コスト：このサービスは、年間18,000件の住宅問い合わせの40%を
£8.50の電話から£0.20のデジタル取引へ移行させると予測されていた
  = 7,200 × (£8.50 − £0.20) = 見逃された£59,760/年、およそ
    2か月の遅延に按分すると ≈ £9,960

不合格評価の総コスト ≈ £49,610
```

この算術の要点は精度ではなく、不合格評価が実際の計算可能な価格を持つということである——それこそがまさに、このゲートに牙がある理由である。

## ソフトウェア開発との関連

エンジニアにとって、この標準は政策文書と同じくらいアーキテクチャと提供のチェックリストとして読める——第11項目（「正しいツールと技術を選ぶ」）と第12項目（「新しいソースコードをオープンにする」）は直接的なエンジニアリング上の決定であり、第14項目（「信頼できるサービスを運用する」）は、あらゆる本番システムが必要とするのと同じSLOとインシデントプロセスを求める。これは本章の包括的な枠組みである——[取引あたりコスト](../cost-per-transaction/)と[チャネル移行による節約](../channel-shift-savings/)はこの標準が財務的に保護しようとしているものであり、[デジタル・インクルージョン](../digital-inclusion/)は第5項目が保証するために存在するものであり、[Government as a Platform](../government-as-a-platform/)のコンポーネント（GOV.UK Notify、Pay、One Login）は、ほとんどデフォルトで第13項目（「オープン標準、共通コンポーネント、パターンを使用し貢献する」）を満たす。「正しいツール」の項目が調達の決定でどう展開するかについては[政府における内製か購入か](../build-vs-buy-in-government/)も参照。

## 落とし穴

- **評価をローンチ日のコンプライアンスチェックボックスとして扱うこと**：ベータ評価の1週間前に初めて14項目を読むチームは予測可能に不合格になる。この標準は、事後的に監査するためではなく、発見の段階から決定を形作るために意図されている。
- **サービスではなくプロトタイプを評価すること**：洗練されたデモは、ライブで、支援付きデジタルを含み、インシデント管理された実際のサービスであれば不合格になるであろうレビューに合格しうる——評価者はこのギャップを探るよう意図されているが、自己認証された小規模サービスはしばしばこれをスキップする。
- **規模拡大前の再評価がないこと**：5%の展開で評価されたサービスは、100%で自動的に準拠したままではない——負荷、失敗需要、エッジケースの利用者はすべて変化する。
- **Service Standardをデザインシステムと混同すること**：GOV.UK Design Systemのコンポーネントは一部の項目（一貫性、アクセシビリティ）を満たすが、この標準はチーム構造、アジャイル実務、データ倫理もカバーする——見た目の良いサービスでも第2、6、9項目で不合格になりうる。
