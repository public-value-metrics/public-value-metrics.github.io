# 面向公共價值的 DORA 指標

DORA（DevOps Research and Assessment，DevOps 研究與評估）指標——部署頻率、變更前置時間、變更失敗率、服務恢復時間，加上作為第五項的可靠性——是軟體行業驗證最充分的交付績效基準。轉化為公共部門問責制的語言後，每一項都直接代理著公共價值到達公民手中的速度與安全程度。

## 為何重要

DORA 長達十年的研究，以《Accelerate DevOps 現狀報告》（*Accelerate State of DevOps Report*）的形式每年釋出（Forsgren、Humble 和 Kim 提出的方法論，如今由 Google Cloud 營運），將團隊分為精英級、高績效、中等績效和低績效四類。精英團隊按需部署，從提交到生產環境用時不到一天，變更失敗率約為 5%，恢復時間不到一小時；低績效團隊每月部署一次或更少，用時數月，變更失敗率約為 40%，恢復需要數週。在政府領域，這些不是工程虛榮指標：政府數位服務局的服務標準要求團隊"頻繁迭代與改進"，並能快速回應使用者需求，而那些無法安全、頻繁部署的部門，無論其使用者研究結果如何，在結構上都無法達到這一標準。內閣辦公室自身的數位效率研究發現，將一位公民從失敗或緩慢的數位交易推向電話或紙質渠道代價高昂——GDS 2012 年的《數位效率報告》估計，某些數位交易的成本低至 20 便士，而電話或面對面接觸的成本可高達 8.62 英鎊——因此面向公眾服務中的一次變更失敗，不僅耗費工程時間，還會將真金白銀推向呼叫中心預算（參見[渠道轉移節約](../渠道轉移節約/)）。

## 數學原理

```
部署頻率        = 生產環境部署次數 / 時間
變更前置時間    = t(部署) − t(提交)，取中位數
變更失敗率      = 失敗變更數 / 變更總數 × 100
服務恢復時間（MTTR） = t(恢復) − t(故障)，取中位數
可靠性          = 服務級別目標（SLO）達成率（可用性、延遲、正確性）
```

公共價值轉化：

```
前置時間   → 流水線中滯留的週數 × 延遲成本，參見 cost-of-delay-in-public-programmes
失敗率     → 面向公民的事件率：變更失敗率 × 每次被轉移到呼叫中心
             的通話成本（或每一次失敗的法定交易成本）
恢復時間   → 服務中斷損害：MTTR × （每小時被阻塞的申領/
             申請數）× 單位下游成本或福祉損失
可靠性     → 效益折扣：一項可用性為 99% 的服務，實際交付其
             建模效益的約 0.99——這是採用率或合規缺口在
             交付層面的對應物
```

## 實例演算

某地方政府福利申領門戶團隊，在一項交付工程投資前後的表現：

```
                    之前        之後
部署                每月一次    每週一次
前置時間            8 周        5 天
變更失敗率          30%         10%
MTTR                3 天        4 小時
```

該團隊每年上線約 25 項改進，平均每項價值為每週 8,000 英鎊（[延遲成本](../公共專案中的延遲成本/)）。將前置時間縮短約 7.3 周，使每項改進的效益流提前到來：25 × 7.3 × 8,000 ≈ **每年 1,460,000 英鎊**的價值被更早交付。就失敗率而言：25 × (0.30 − 0.10) = 每年減少 5 次失敗變更；一個面向公眾的門戶上的一次失敗變更，通常估計會將約 2,000 名公民轉移至電話渠道，成本為 8.62 英鎊對比 20 便士，淨成本約為每起事件 8.42 × 2,000 ≈ 16,840 英鎊，因此避免 5 起事件可節省約**每年 84,200 英鎊**。這項交付工程投資，是以與任何其他公共價值論證相同的"貨幣"來估值的。

## 實例演算續：可靠性

如果該門戶的可用性為 97%，而非目標的 99.5%，且每一個百分點的宕機時間被建模為 2% 的申領因放棄而流失，那麼該服務實際交付的效益約為其建模的每年 200 萬英鎊效益的 0.975——這是一筆每年 50,000 英鎊的效益折扣，一個純粹的正常運作時間儀表盤永遠不會揭示出這一點。

## 與軟體工程的關聯

DORA 指標其實是公共服務營運指標換了一套外衣：前置時間對應[服務標準與交易指標](../服務標準與交易指標/)；變更失敗率對應返工率和投訴率；MTTR 對應一項法定服務對申領人不可用的時長。改進技術可以雙向遷移，因為兩者本質上都是在問責制約束下運作的排隊系統——關於其背後的排隊論數學，參見[政府交付中的流動指標](../政府交付中的流動指標/)。另請留意 DORA 2025 年的發現：AI 的採用與更高的吞吐量相關，但也與*更差*的穩定性相關——這是一項兼具功效與副作用的介入措施，正是本章[AI 生產力](../公共部門中的-ai-生產力/)主題所要梳理的那種淨收益分析。

## 常見陷阱

- **指標操縱**：用無實際意義的空釋出來虛增部署計數，或將熱修復排除在變更失敗計數之外。應像法定服務標準定義"成功交易"那樣精確地定義各類事件。
- **跨部門排行榜**：DORA 分級比較的是交付實踐，而不是風險特徵各異的服務；一個稅款支付系統被評為"高績效"可能恰恰是正確的姿態，因為考慮到保證要求，"精英級"反而可能是輕率的。
- **單獨最佳化某一項指標**：只追求速度而不顧變更失敗率，是經典的吞吐量與穩定性權衡陷阱——應將四項指標一併報告，而不是壓縮成單一分數。
