# 政府交付中的流動指標

流動指標——利特爾法則（Little's Law）、在製品（WIP）限制和流動效率——描述的是工作在一個容量有限的系統中流轉的速度。一塊衝刺看板就是這樣一個系統；一條福利申領佇列、一份規劃申請登記冊，或一批簽證個案積壓，本質上是同一套數學、只是穿著不同的制服。

## 為何重要

政府的案件負荷本質上是排隊系統，而排隊系統無論有沒有人去測量，都遵循排隊論的規律。法定裁定期限將這一點明確化：在《城鄉規劃法》體制下，大多數小型規劃申請都有 8 周的法定裁定目標，重大申請則為 13 周——一項直接寫入法律的週期時間承諾。內政部的庇護個案積壓問題，經國家審計署和內政事務特別委員會反覆審查，是一個有充分記錄的公共系統案例：在長期持續的時間裡，在製品的增長速度超過了吞吐量，導致週期時間遠遠超出任何法定或服務預期。流動指標為工程師和個案管理經理提供了一套共同的、量化的詞彙，來精確描述這種失敗模式，而不是將其留作一個定性的"積壓問題"。

## 數學原理

```
利特爾法則：  在製品數 = 吞吐量 × 週期時間
         →   週期時間 = 在製品數 / 吞吐量

流動效率 = 有效（處理）時間 / 總週期時間   （Vacanti）

在製品限制效應：在吞吐量固定的情況下，將在製品數減半
大致會使平均週期時間減半（利特爾法則的變形）——這是
一個無需增加人手即可運用的槓桿。
```

關於將同樣的數學應用於軟體部署流水線而非個案處理的對應做法，參見[面向公共價值的 DORA 指標](../面向公共價值的-dora-指標/)。

## 實例演算

**某地方政府規劃部門**：任意時刻在辦申請數（在製品）為 400 宗，團隊每週處理 50 宗申請（吞吐量）。

```
週期時間 = 在製品數 / 吞吐量 = 400 / 50 = 8 周
```

這恰好達到小型申請 8 周的法定目標——沒有任何緩衝餘地，這意味著任何進入需求的波動，或任何被諮詢方回應時間的波動，都會將裁定推向超出法定期限。

**流動效率**：在這 8 周（56 個日曆日）中，一宗申請通常只有大約 6 小時的實際個案工作人員處理時間。

```
流動效率 = 6 小時 / (56 天 × 每天 8 個工作小時)
         = 6 / 448 ≈ 1.3%
```

Vacanti 為軟體團隊設定的基準是典型流動效率為 15%至20%；而政府個案處理，由於涉及多個法定諮詢方的交接和公眾諮詢視窗期，其流動效率往往要低一個數量級。那 98.7% 的"等待"時間，才是這八週真正消耗掉的地方——而不是消耗在個案工作人員的處理能力上。

**在製品限制介入**：將每位個案工作人員的在辦申請上限從不設限的 25 宗降至 15 宗（保持吞吐量不變），會使一個 16 人團隊的在製品數從 400 降至約 240：

```
新週期時間 = 240 / 50 = 4.8 周
```

一項政策變化——而非增加人手——就使週期時間接近減半。這正是 DORA 式交付團隊限制衝刺在製品數量時所運用的同一槓桿。

## 與軟體工程的關聯

流動指標是交付團隊的看板與其所建置軟體所服務的個案處理一線之間的共同語言：個案工作人員的佇列與拉取請求（pull request）佇列同樣受利特爾法則支配，也以同樣的方式突破各自的週期時間目標——相對於吞吐量而言在製品過多。這與[公共專案中的延遲成本](../公共專案中的延遲成本/)直接相關：週期時間 × 延遲成本，就是此刻正滯留在佇列中的英鎊數；這也與[服務標準與交易指標](../服務標準與交易指標/)相關——一項已公佈的處理週期目標，本質上是一項週期時間承諾，只有流動指標才能在它未被達成時診斷出原因。一套個案處理系統的軟體，應當將在製品數和週期時間作為一等營運指標展示出來，而不是將它們埋藏在一個無人查詢的個案管理系統內部。

## 常見陷阱

- **在不解決真正瓶頸的情況下新增在製品限制**：如果約束來自外部法定諮詢方的回應時間，限制個案工作人員的在製品數只會把佇列推向上游，而不會真正縮短週期時間。
- **將流動效率當作可操縱的目標**：加快那 1.3% 的有效處理時間對週期時間的影響微乎其微；槓桿幾乎總是在等待狀態之中，這通常意味著需要流程重新設計，而不是加快個案工作人員的處理速度。
- **忽視波動性**：利特爾法則描述的是平均值；一個需求波動性高的案件負荷需要緩衝產能，而不僅僅是更嚴格的在製品限制，否則即便平均值有所改善，法定期限仍會在波動的尾部案例上被錯過。
- **不一致地測量在製品**：一宗在記錄系統中顯示為"在辦"但實際上正因等待第三方而停滯的案件，仍然是在製品；將其排除在外會美化數位，卻不會改變公民所面對的實際情況。
