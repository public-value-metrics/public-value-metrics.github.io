# 政府即平臺（GaaP）

"政府即平臺"是這樣一種策略：將共享的、可複用的元件——一項通知服務、一項支付服務、一項身份驗證服務——只在中央層面建置一次，從而使成百上千項獨立的政府服務能夠直接呼叫它們，而不是各自重複建置。它將公共數位基礎設施重新定位為一個平臺經濟學問題：價值不在於任何一次具體的整合，而在於*下一個*採用它的團隊所面對的邊際成本趨近於零。

## 為何重要

政府數位服務局（GDS）在其 2015 年釋出的《政府即平臺》（"Government as a Platform"）出版物中正式提出了這一策略，指出政府一直在一個又一個服務中分別重複建置相同的能力——收取支付、使用者通知、身份驗證、地址查詢——每一次都各自承擔採購、安全評估和持續支援的負擔。替代方案是建置少數幾個共享平臺，一次性建成高標準並在各處複用：用於傳送電子郵件、簡訊和信件的 GOV.UK Notify、用於線上收款的 GOV.UK Pay，以及用於身份驗證的 GOV.UK One Login（早期 GOV.UK Verify 身份專案的後繼者）。這些平臺所達到的規模，正是這一策略行之有效的最清晰證據：GOV.UK Pay 已在約 1,800 項獨立服務中處理了超過 100 億英鎊的交易額——處理第一個 10 億英鎊用了約四年時間，如今處理同樣的金額只需約五個月——而 GOV.UK Notify 已代表超過 1,500 個政府機構傳送了超過 90 億條訊息。每一個採用這些平臺的服務，都省去了自行建置、保障和維護支付閘道器或訊息傳送流水線的負擔。

## 數學原理

```
每項服務的建設成本（無平臺）= N 項服務 × 建置、安全評估
  並運作一套支付/通知/身份驗證系統的成本

平臺成本 = 固定的平臺建設成本
         + 每個採用平臺的服務的邊際成本
           （整合、配置、持續的平臺團隊支援）

複用實現盈虧平衡的條件：
  平臺建設成本 < N × （單項服務建設成本 − 邊際整合成本）

對於一個成熟的平臺而言，每新增一個採用者的邊際成本
會趨近於僅剩交易/訊息費用本身——固定成本被攤銷到
整個政府資產範圍內，而不是由某一個部門的預算獨自承擔，
這正是 GaaP 元件通常由中央出資、而不是向早期採用者
按全成本收回費用的原因。
```

## 實例演算

**某地方政府採用 GOV.UK Pay，而不是自建支付閘道器**：

```
自建方案估算：
  PCI-DSS 合規工作 + 整合 + 持續維護
  ≈ 85,000 英鎊建設成本 + 22,000 英鎊/年維護成本

採用 GOV.UK Pay：
  整合工作量 ≈ 12,000 英鎊（開發者工時）
  交易費用：政府對公民的銀行卡支付通常按小比例
  加每筆固定費用收取，議會無需另行承擔 PCI-DSS
  合規負擔
  ≈ 一次性 12,000 英鎊，後續成本隨交易量變化而非固定

首年節省 ≈ 85,000 − 12,000 = 73,000 英鎊，這還不包括
避免的每年 22,000 英鎊維護成本，以及避免在議會自營
系統中持有銀行卡資料所帶來的合規風險——後一類價值
在 public-sector-cybersecurity-value 中有所論述。
```

將這 73,000 英鎊的節省乘以目前使用 GOV.UK Pay 的約 1,800 項服務，政府整體避免的建設成本合計將達到數億英鎊之巨——這一策略的真正價值所在，正是平臺經濟學本身，而不是任何單次整合。

## 與軟體工程的關聯

"政府即平臺"是支援[政府中的自建與外購之爭](../政府中的自建與外購之爭/)的一個直接論據：當一個已經過評估、運作良好的共享元件存在時，建置一個定製的等價物，在物有所值方面幾乎從來都不是更優的選擇，而且幾乎從定義上就會未透過[數位服務標準](../數位服務標準/)第 13 條（"使用並貢獻於開放標準、通用元件與設計模式"）。它也改變了[政府 IT 中的總擁有成本](../政府-it-中的總擁有成本/)的形態：採用平臺，是用一大筆資本和維護支出，換成一筆更小、與使用量掛鉤的營運成本，這更容易預測，也更容易在某項服務下線時停止資助。元件的開放複用，在[開放資料的價值](../開放資料的價值/)中有一個同類做法——兩者都是將政府生產一次的東西，當作共享基礎設施而非部門資產來對待的策略。

## 常見陷阱

- **暗中重複自建**：團隊因為平臺的接入流程比自己動手更慢，而悄悄建置自己的支付或通知整合方案——這是一個治理摩擦問題，而非技術問題，它會在不知不覺中侵蝕整個策略所依賴的複用經濟學。
- **平臺團隊獲得的資金與其創造的價值不成比例**：價值累積在使用該平臺的各部門，而成本則由平臺團隊承擔，這會造成長期投入不足的風險，除非資金來源集中且受到保護——這是"公地悲劇"的一種變體。
- **僅以使用量衡量平臺的成功**：採用數位（已接入的服務數、已傳送的訊息數）是一個領先指標，而不是價值的證明；真正的檢驗標準是上文所述的避免建設成本與避免風險的算式。
- **將"平臺"等同於"單體系統"**：GaaP 元件之所以成功，是因為每一個都透過狹窄、穩定的介面把一件事做好；將互不相關的能力捆綁進同一個"平臺"，只是在另一個尺度上重現了定製自建的問題。
